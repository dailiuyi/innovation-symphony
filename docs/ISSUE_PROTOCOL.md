# Issue 交互协议草案

状态：部分需求已确认，永久协议的具体语法与运行细节仍待讨论。V0 已实现 GitHub 轮询读取与确定性评论解析，当前工程默认见 [IMPLEMENTATION_V0.md](IMPLEMENTATION_V0.md)；尚未进行真实平台接入验收。

## 已确认的交互顺序

创建 Issue → 可选的独立模型指令评论 → 添加 ready 标签 → 机器人自动发现、领取并开始执行。

不要求先指派机器人。模型缺省时按仓库、按角色使用默认值；模型标签不参与路由。机器人领取后是否自动设置 assignee 是展示实现选项，尚未决定，也不能成为要求用户手动指派的前提。

## 候选命令格式

建议在一条独立 Issue 评论中输入：

```text
/symphony models coder=gpt-6-sol reviewer=gpt-6-astra
```

也可以设计为仅指定某个角色：

```text
/symphony models coder=gpt-6-sol
```

V0 采用这两种形式作为工程默认，尚非已发布的永久接口；模型 ID 仅举例，不保证当前提供商可用。程序解析命令前缀和键值字段，再从模型白名单中校验，不使用大模型猜测自由文本。

## 建议的解析与执行边界

以下待讨论，不当作已批准产品行为：

- 只接受获准成员的独立命令评论，忽略普通讨论、引用和机器人回声。
- 对评论作者、时间、事件/评论 ID、配置版本和执行轮次留痕。
- 在开始执行前冻结本轮模型选择，后续新评论不悄悄改写在途任务。
- 无效/不可用模型给出明确原因，不静默换到另一个模型。
- 对重复事件做幂等处理，避免重复领取；将是否运行与派发尝试记录持久化。

需要单独决定：采用最后一条完整命令还是逐角色累计；编辑/删除评论；重启扫描存量 ready；添加 ready 与评论事件乱序；运行中切换或重新执行；默认值变更何时生效。

## 标签

已确认的语义：ready 表示任务可领取，review 和 blocked 表示相应状态。精确标签名（例如是否使用 `symphony:` 前缀）、执行中/完成状态、移除 ready 时的行为及谁能驱动状态转换尚待确认。

机器人账号名称、认证、模型外发策略与能派发任务的成员范围同样待设计。本文件不授予对当前博客或公司仓库的实际派发权限。
