## 基线与判断

用户本轮明确项目原型为 [openai/symphony](https://github.com/openai/symphony)。以官方规范和参考实现为设计对照；旧博客控制器仅作为历史经验来源，不作为默认必须迁入的实现。采用官方实现、按规范另行实现或选择语言均待定。

本轮在线读取了官方 main 的 [SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md) 和 [Elixir README](https://github.com/openai/symphony/blob/main/elixir/README.md)。读取的是浮动分支，GitHub API 限流导致未固定提交 SHA；本快照不宣称与未来 main 一致，也未运行官方代码。

独立 Reviewer 未发现当前已确认决策之间的实质矛盾。主要问题是执行合同尚未闭合，不是已证实的运行故障。建议保留官方调度核心边界，逐项决定新增策略，不急于引入分布式服务。

## 优先审核项

1. **领取与编码之间的门禁。** `OPEN_QUESTIONS.md` 第 1 项未决定是否先计划后确认；不能把 ready 的自动领取解释成所有后续动作都获授权。
2. **状态与恢复。** 定义首次接入存量 ready、重复扫描、ready 移除/重加、重启以及在途任务的语义；决定标签由谁维护。
3. **交付终点。** 候选分支、Draft PR/MR、Review、合并、发布分别停在哪里；Review 通过不自然等于完整业务验收。
4. **权限与配置。** ready/模型/后台配置的操作者范围、提供商允许范围、配置版本及变更生效时间；UI 与 `WORKFLOW.md` 的唯一写入归属。
5. **部署与验收。** 先评估现有 CI，平台工具链与设备决定执行环境；逻辑模块不等于需要独立微服务。统一管理不等于跨仓库编排。

初次审查建议先讨论第 1 项。IS-012 已确认 GitHub MVP 先行；当前先讨论自身迭代的交付与升级边界，其他问题保持待定。候选验收条件见 [SELF_ITERATION_MVP.md](SELF_ITERATION_MVP.md)。
