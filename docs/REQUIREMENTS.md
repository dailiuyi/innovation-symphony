# 已确认需求

日期：2026-09-28。来源：项目所有者在框架抽取讨论中的明确选择。当前开始本地 MVP 实现；真实平台接入与两轮自身迭代尚未验收。

## 产品与部署

项目原型与设计参考基线为 [OpenAI Symphony](https://github.com/openai/symphony)（本轮补充，见 IS-010）。已确认直接基于官方源码修改（IS-014），复用其 Elixir 实现；旧博客实现仅作经验参考。

项目名称为 `innovation-symphony`，提供统一管理、可供多个 repo 复用的 Symphony 框架。主要面向 Unity、Android、iOS，兼顾用户负责的 Web 项目。

长期目标部署到云端，不依赖个人电脑持续运行。首期环境、云提供商、执行节点位置和操作系统尚未决定；不预设所有平台可以在同一种云主机上完成构建。

## 平台与任务范围

平台分期已更新（IS-012）：MVP 先实现 GitHub，随后由 Symphony 迭代自身；GitLab 后置，双平台仍为后续目标，不再要求 MVP 同时支持。一个 Issue 对应所属仓库内的任务，仓库之间独立执行，不包含跨仓库修改或任务编排。

## 任务入口

用户在代码平台的 Issue 中描述需求，可先发一条独立评论指定模型，然后添加 ready 标签。机器人自动发现带 ready 标签的 Issue，领取并开始执行；不要求用户预先将 Issue 指派给机器人。

ready 表示可开始执行，review、blocked 等标签表达基本工作流状态。模型配置不放在标签中。标签是否带命名空间、完整状态集合以及谁维护状态转换尚待确认。

初次接入已有 ready Issue、重复扫描、移除/重新添加 ready、重启与中断恢复的规则尚未确定。它们不能默认复制旧博客的“只认新标签事件”合同。

## 模型配置

- 每个仓库可以分别选择默认编码模型与默认 Review 模型。
- 用户在独立 Issue 评论中通过约定格式指定模型，由程序读取并确定性解析，无需大模型理解普通讨论。
- 按角色解析：用户显式指定值优先；未指定该角色时沿用对应仓库默认值。
- 评论具体语法、可用模型列表、权限、命令编辑/冲突和运行中变更规则见 [协议草案](ISSUE_PROTOCOL.md)，尚未全部定案。

## 后台

第一版先制作最简单的查看型原型，展示仓库、任务进度、日志、结果和费用。同时保留编码模型与 Review 模型两个独立配置入口，按仓库设置默认值。

已实现原型的选项是演示数据，不证明模型可用或具备使用授权。真实配置持久化与费用核算尚未实现。

## 开发自身与迭代方式

已确认实施方向：先做 GitHub 最小 MVP，再由 Symphony 迭代 Symphony 自身（IS-011、IS-012）。自动编码、机器检查、独立 Review 与 PR 交付已确认；合并和升级由人工决定（IS-013）。HTML 仍是演示，真实接入需仓库和凭据。

已确认人工合并及升级；具体安装切换、隔离强度和恢复机制仍是工程提案。私有仓库与真实 Issue #1 已接入；首轮由 V0 生成候选，但因检查环境污染停止，未通过交付验收。用户已授权修复环境隔离后显式重跑（IS-017），不改变检查失败停止和人工合并边界。模型配置和查看型后台的需求保留，其 MVP 实现深度待讨论。如何证明自身迭代能力见 [GitHub MVP 与自身迭代验收提案](SELF_ITERATION_MVP.md)，其中两轮接棒、回退演练仍未执行；工程默认见 IMPLEMENTATION_V0.md。

用户要求在逐步讨论中确认需求；已确认项、建议与待讨论项必须分开记录。独立创建项目不等于批准全部候选架构或立即开发完整平台。

## GH-1 有限返工

按 IS-015/016 及本轮执行规格，仅有效独立 Review 明确拒绝时最多返工两次，每次先回帖原 Issue；模型及初始 base 冻结，逐轮保留证据。失败或中断不自动恢复，交付仍止于 Draft PR。工程兼容默认 `max_rework=0`，显式 1/2 启用。实现和验收对应见 [REVIEW_REWORK.md](REVIEW_REWORK.md)，真实执行验收尚未完成。
