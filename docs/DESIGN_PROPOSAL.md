## 来源实现的参考价值

2026-09-28 用户补充：项目原型为 [openai/symphony](https://github.com/openai/symphony)（IS-010）。架构以官方规范和参考实现为对照；下文旧博客抽取路线仅为候选。当前官方参考实现已列出 GitHub Issues 与 GitLab 适配器，应先评估复用与语义差异，不能假定双平台接入必需从零重写。在线核对范围与差异见 [架构审核快照](ARCHITECTURE_REVIEW.md)。

讨论时核对了博客项目的公共 Python 验收包、独立安装快照及 GitHub/浏览器耦合点。可复用思路包括编码、检查、独立 Review、有限返工和版本化安装；不代表这些能力已进入本项目。来源项目仍有其他任务的未提交改动，不能把整个工作树直接当作框架的稳定基线。

## 建议的最小框架边界

建议使用一个独立框架仓库，先保持一个可安装版本和清晰模块，不急于拆成多个服务。

| 模块 | 负责的内容 | 不应固定在其中的内容 |
| --- | --- | --- |
| 核心控制器 | 任务生命周期、计划与授权绑定、重试预算、并发、取消、恢复、证据索引 | 博客主题、具体构建命令、设备型号 |
| 代码托管适配层 | 任务、标签或事件、PR/MR、提交检查、审查回复、仓库地址 | github.com 固定地址或某个用户账号 |
| Agent 适配层 | 模型能力、会话、结构化结果、提供商路由 | 绕过公司代码外发策略 |
| 执行节点 | 按能力领取任务，在隔离目录运行，回传日志和产物 | 各项目独立复制整套控制器 |
| 项目与验收适配层 | 工具链版本、准备/构建/测试命令、证据采集、允许路径 | 用一套网页截图标准评价所有端 |

任务至少绑定 project/repository、plan hash、候选 SHA、适配器/工具链版本、执行节点、尝试编号和产物哈希。执行节点申报 OS、SDK、Unity/Xcode 版本、可用设备与并发容量。调度对设备和许可证等稀缺资源使用互斥租约；断线重派后，旧执行结果不能覆盖新轮次。

平台分期已按 IS-012 更新：先实现 GitHub MVP，GitLab 后置。先验证本项目在 GitHub 上的 ready 发现、任务执行及交付闭环；后续 GitLab 适配仍需覆盖身份、状态、MR 和检查结果等语义。具体实例及认证环境待确认，旧博客可作为后续回归样本，不作为 MVP 的前置接入要求。

## 用 Symphony 开发 Symphony

已确认方向（IS-011、IS-012）：先完成 GitHub 最小 MVP，再由 Symphony 迭代自身。能力证明与接棒演练见 [自身迭代验收提案](SELF_ITERATION_MVP.md)，其中具体验收门槛尚未批准。下面的“稳定版调度候选版开发”是实现该方向的候选方式，隔离、验收与升级细节仍待讨论：

1. 操作者先建立框架源码、独立项目配置及可信验收入口。这一启动步骤由受控的主机操作完成。
2. 稳定版本 A 调度框架仓库的普通开发任务，在隔离工作区生成候选版本 B；运行中的 A 与其策略、凭据、状态不向任务开放写权限。
3. B 先通过核心回归、适配器契约与故障恢复测试，再在独立状态目录、端口和测试任务队列中运行。不得同时消费正式任务队列。
4. 修改授权、沙箱、计划门禁、验收或安装逻辑的任务采用额外独立审查。候选版附带的测试可增加覆盖，但不能单独决定自身可信；稳定基线检查由任务之外维护。
5. 获准升级后停止新任务接入，确认活动任务安全结束并备份状态，再安装已验收的固定版本。切换失败按已验证方案回退；状态格式升级需要兼容检查或备份恢复，不能只回退可执行文件。

开发产出、自动验收、人工批准、安装及正式发布分别记录。自举开发不意味着自动改写自己的授权，也不意味着验收通过就自动升级服务。

## 各端接入与验收

| 项目 | 建议的初始执行能力 | 可自动化证据 | 仍需单独安排的验收 |
| --- | --- | --- | --- |
| Unity | 匹配项目版本的 Editor、构建目标模块、许可证及必要图形环境 | 编译、EditMode/PlayMode、构建包、日志、可重复场景截图/录像 | 真机性能、画面与手感、AR/多人交互 |
| Android | JDK、Gradle、Android SDK、模拟器或测试设备 | 单元测试、Lint、仪器测试、APK/AAB、截图和日志 | 目标机型兼容性、性能及发布签名流程 |
| iOS | macOS 执行节点、Xcode、模拟器或测试设备 | xcodebuild 构建测试、测试结果包、截图和日志 | 真机能力、证书与描述文件、发布签名和商店交付 |
| Web | Node 与浏览器环境 | 构建、单元/端到端测试、截图和交互结果 | 获准部署后的线上版本验收 |

各端都不把“构建通过”等同于完整验收。Unity 资源与场景变更需关注 .meta/GUID、序列化及资源冲突；缓存应按项目与工具链版本管理，工作区仍须隔离。发布签名凭据留在受控构建/发布链路，不默认提供给编码 Agent。

现有 CI Runner 能承接的构建测试应优先复用；新增执行节点协议用于当前 CI 无法覆盖的交互或设备任务，避免重复建设两个构建调度系统。

## 建议的实施次序与通过条件

按 IS-011 调整优先次序；旧的“先博客抽取、公司试点，再自身开发”不再是当前路线。以下阶段划分和通过条件仍为建议，不是已确认的 MVP 功能清单：

1. **收敛 MVP**：以官方 Symphony 为参考，确认代码复用方式与 GitHub 上的最小执行闭环；GitLab 后置已确认。旧博客经验可参考，抽取其控制器不是必经步骤。
2. **建立最小可执行闭环**：建议先让本项目的一个小范围 Issue 经 ready 领取、隔离编码、检查与 Review，产生可供人工审核的结果；具体交付形式和执行前门禁待定。具备可追踪日志及明确失败状态，能判定是否重复派发。静态 HTML 不作为此阶段已完成的证据。
3. **由 Symphony 迭代自身**：建议先处理小缺陷、测试与配置能力，再逐步扩展。运行版本与候选版本隔离、人工批准后升级为候选机制，不能理解为运行中自动覆盖自己。
4. **扩展业务接入**：在自身迭代闭环成立后，按后续双平台目标及已确认需求补齐相应能力，并安排 Unity 与 Android/iOS 等项目试点。具体节点、设备及云环境据实际需求决定。
5. **推广**：根据试点证据完善授权、预算、审计、产物保留和节点容量。首期不需要为了画全架构而先实现所有候选模块。

试点同时记录端到端耗时、人工实际介入时间、返工次数、误判验收、模型成本、构建资源和失败原因。与人工/原 CI 基线比较，不只统计提交或任务数量。重复事件、进程中断、失效节点、过期证据和权限不足要能得到可预测结果。

框架边界的关键通过条件：第二个不同技术栈项目主要通过适配器和项目配置接入，而不是复制或大量改写核心控制器。首批任务优先选择逻辑缺陷、测试补齐、构建修复、小范围 UI；复杂场景/资源、性能和真机交互保留对应人工环节。

试点前需确认：GitLab/GitHub 的具体实例及可用权限、各端项目负责人、现有 CI、可用 Windows/macOS 构建节点、设备/许可证，以及公司代码能使用哪些模型提供商。这些信息影响部署方案，不影响框架拆分方向的可行性判断。
