# Issue 草案 001 · Review 不通过自动返工，理由回帖原 Issue

- 来源：项目所有者 2026-09-28 会话陈述（下一阶段想添加的功能）。
- 状态：首轮范围已由用户确认（IS-015/016），下方“本轮执行规格”是本次执行依据。尚未通过实际执行验收。
- 落地：`dailiuyi/innovation-symphony` 私有仓库；由已提交的 V0 执行本任务，结果停在 Draft PR，由人工合并升级。

## 本轮执行规格（用户已确认）

1. 仅独立 Review 的有效结论明确拒绝时自动返工，最多 2 次，即最多 3 轮编码/检查/Review。检查失败、模型错误、非法 Review 输出都停止，不当作可返工的有效拒绝。
2. 同一工作区继续修改；本任务的原始 base SHA 不变，每轮拥有自己的 candidate SHA、模型、检查日志、Review 和用量记录。每轮重新检查并使用新的只读 Review 会话。
3. 在触发下一轮前，将本轮拒绝理由评论到原 Issue，记录评论 ID、轮次和候选 SHA。评论写入失败或结果不确定时停止，不盲目重发或继续花费；用持久意图和只读对账避免重复评论。超限后的最后一次拒绝也必须回帖。
4. 返工次数在启动前持久记录；重复扫描及重启不能把计数归零。中断保持阻塞，不自动恢复。编码与 Review 模型沿用领取时冻结值，运行中评论不更换模型。
5. 评论不 @ 提及用户；不自动修改标签。返工通过后最多交付一个 Draft PR；不能自动合并、安装或升级运行版本。
6. Review 同时评估代码与测试的断言强度、验收标准对应关系和失败敏感性。审查结论须能追溯验收条目与测试；测试不合格也是明确拒绝理由。优先用审查推理及有意义的回归测试验证，不引入全仓库强制变异测试平台。
7. 用量累计记录实际可得值；费用或用量缺失明确为 unknown/null，不能记成已知 0。只增加本功能所需的可追溯数据，不扩展演示后台为计费系统。
8. 全部验收条目应有对应自动化测试，包含评论不确定/超限/中断/测试不合格等失败路径。按仓库既有门禁执行格式、lint、100% 覆盖率、Dialyzer、构建及外部冻结基线测试。

### 本轮兼容约束与工程范围

- `max_rework` 支持 0..2，0 保持旧版无返工路径及现有测试兼容；默认继续为 0，显式设为 1/2 时启用本轮返工与理由回帖合同。此为 V0 向 V1 的工程兼容安排，不代表改变已确认的返工能力。
- 不重写官方调度器，不修改运行中的 V0、控制器配置、外部基线/证据或 Git 元数据。代码只在任务工作区修改，由控制器提交、推送和创建 PR。
- 原 `max_rework=1` 非法断言已由操作者在派发前改为拒绝 3，以兼容明确批准的新上限。其余冻结基线必须继续通过，不以删除测试、修改覆盖阈值或忽略模块获得通过。
- 全局预算、完整标签状态机、自动恢复、自动升级及计费后台不属于本轮。历史未定案草稿保留在 V0 提交记录中。

建议标题：`Review 不通过后自动打回编码重做，并把不通过理由评论回原 Issue`

建议标签：`enhancement`（标签命名规范尚未定案，见 OPEN_QUESTIONS 第 5 项）。

## 背景：当前行为与预期的差距

当前 GitHub MVP 流程：ready Issue 自动领取 → 编码 bot 编码 → 控制器执行检查 → 独立 Review bot 只读审查 → 通过后由控制器建 Draft PR，等待人工合并。

差距在失败分支：

1. Review 判定不通过（或检查失败）时，任务直接进入 blocked，**不会自动打回编码 bot 重做**（返工上限 `max_rework` 当前固定为 0）。
2. 不通过理由只保存在回执 JSON、证据目录（`review.json`、`check-N.log`）和后台运行状态里，**不会以评论形式出现在原 GitHub Issue**，用户在平台上看不到失败原因。

## 需求（用户已确认的方向）

1. Review bot 判定不通过后，任务自动打回编码 bot 重做，而不是直接阻塞等待人工。
2. 每次不通过时，不通过的理由必须回帖到原 GitHub Issue，让人在 Issue 上直接看到为什么被打回。
3. 返工通过后，流程与现状一致：控制器创建 Draft PR，由用户人工审核与合并。不改变 IS-013/014 的交付边界（无自动合并、无自动升级）。
4. 实现必须附带与本 Issue 验收标准对应的测试；没有对应测试的验收标准视为未实现。
5. Review bot 除审查实现代码外，必须同时审查测试本身，审查维度包括：
   - **断言强度**：测试是否真的断言了行为结果，而不是只跑一遍不校验、或断言过弱（例如仅检查"不抛异常"）。
   - **与 Issue 的对应关系**：测试是否覆盖本 Issue 验收标准；哪些标准无测试对应必须指出。
   - **失败敏感性**：实现被破坏（相关逻辑被改错或删除）时测试是否会失败；对"永远通过"的无效测试判定为不合格。

## 实现提示（不限定内部结构）

复用 `mvp/executor.ex` 的单轮流水线、`Mvp.Config.max_rework`、`Mvp.Receipt`、GitHub Client 与独立 AppServer 会话。新增控制器 Issue 评论能力，Agent 平台动态工具保持禁用。优先小范围扩展，不引入第二套调度器、无限循环或独立计费系统。

Review 维度可用结构化字段表达，启用返工模式时应由控制器验证；旧版 max_rework=0 的输出与测试保持兼容。评论身份沿用控制器凭据；评论需带可追溯的轮次和候选标识，不能把 Issue/Review 任意文本作为新授权。自动验收记录见本仓库既有验证命令；真实 GitHub 和版本接棒仍需单独报告，不能用模拟测试证明真实上线。
