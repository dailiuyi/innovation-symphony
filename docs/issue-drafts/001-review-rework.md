# Issue 草案 001 · Review 不通过自动返工，理由回帖原 Issue

- 来源：项目所有者 2026-09-28 会话陈述（下一阶段想添加的功能）。
- 状态：需求方向已确认，边界细节待讨论。本稿不是已定案规格；待确认项不得当作实现默认值。
- 落地时机：GitHub 仓库尚未创建（IS-013/014，先本地验证）。建库后可将本稿正文贴为 Issue。

建议标题：`Review 不通过后自动打回编码重做，并把不通过理由评论回原 Issue`

建议标签：`enhancement`（标签命名规范尚未定案，见 OPEN_QUESTIONS 第 5 项）。

## 背景：当前行为与预期的差距

当前 GitHub MVP 流程：ready Issue 自动领取 → 编码 bot 编码 → 控制器执行检查 → 独立 Review bot 只读审查 → 通过后由控制器建 Draft PR，等待人工合并。

差距在失败分支：

1. Review 判定不通过（或检查失败）时，任务直接进入 blocked，**不会自动打回编码 bot 重做**（返工上限 `max_rework` 当前固定为 0）。
2. 不通过理由只保存在回执 JSON、证据目录（`review.json`、`check-N.log`）和后台运行状态里，**不会以评论形式出现在原 GitHub Issue**，用户在平台上看不到失败原因。

## 需求（用户已确认的方向）

1. Review bot 判定不通过后，任务自动打回编码 bot 重做，而不是直接阻塞等待人工。
2. 每次不通过时，不通过的理由必须回帖到原 GitHub Issue，让人在 Issue 上直接看到为什么被打回。
3. 返工通过后，流程与现状一致：控制器创建 Draft PR，由用户人工审核与合并。不改变 IS-013/014 的交付边界（无自动合并、无自动升级）。
4. 实现必须附带与本 Issue 验收标准对应的测试；没有对应测试的验收标准视为未实现。
5. Review bot 除审查实现代码外，必须同时审查测试本身，审查维度包括：
   - **断言强度**：测试是否真的断言了行为结果，而不是只跑一遍不校验、或断言过弱（例如仅检查"不抛异常"）。
   - **与 Issue 的对应关系**：测试是否覆盖本 Issue 验收标准；哪些标准无测试对应必须指出。
   - **失败敏感性**：实现被破坏（相关逻辑被改错或删除）时测试是否会失败；对"永远通过"的无效测试判定为不合格。

## 待确认边界（逐项讨论后再定案）

1. 返工次数上限及超限行为：超过上限后是否 blocked 等人工？上限是全局固定还是每仓库/每 Issue 可配？（关联 OPEN_QUESTIONS 第 7 项）
2. 适用范围：仅 Review 不触发打回，还是构建/测试检查失败也自动打回重做？
3. 打回方式：在同一工作区继续修改，还是每轮全新隔离尝试？回执状态机与候选 SHA、证据如何关联多轮？
4. 理由回帖细节：发帖身份（机器人账号）、评论格式（人可读 summary；是否需要机器可解析的结构标记）、是否 @ 提及添加 ready 的用户。
5. 返工期间的标签流转：ready 保留还是移除？现有 review/blocked 之外是否需要表达"返工中"的状态？谁能驱动转换？
6. 返工进行中用户补发 `/symphony models` 指令是否生效：与"开始前冻结本轮模型选择"的既定原则如何衔接？
7. 费用与预算：多轮尝试的费用是否累计展示？是否需要单 Issue 预算上限打断返工循环？
8. 中断与重启后的恢复：返工中的在途工作区与回执如何恢复，不重复扣费、不重复派发？（轮次计数持久化进回执已列为实现要求，见实现衔接提示。）
9. 测试审查的"失败敏感性"如何判定：由 Review bot 以推理判断，还是需要自动化手段（如变异测试）辅助？判定为不合格测试时的打回范围（仅补测试，还是连同实现一起返工）？
10. "实现附带对应测试"的范围：仅限本次改动新增的验收标准，还是同时要求为改动触碰到的既有行为补测试？

## 实现衔接提示（工程提示，不是承诺或设计定案）

- `mvp/executor.ex` 中 Review 不通过现为 `{:error, :mvp_review_not_approved}`，经 `mvp.ex` 直接进入 blocked；需在此分支改为受上限控制的返工循环。
- `Mvp.Config` 已有 `max_rework` 字段，且当前显式拒绝非 0 值（校验报 `:mvp_rework_not_supported`）；实施时把该校验放开到 0..N 即成为返工上限入口。
- 返工轮次计数必须持久化在回执中，与回执"重启后保持阻塞、at-most-once"的既有语义一致；重启不得清零轮次，否则会绕过上限重复执行。
- 回执状态机（claimed → preparing → coding → checking → reviewing → publish_pending → blocked）需扩展返工相关状态；证据目录需按轮次编号以保留每轮结论。
- 向 Issue 回帖需要 MVP 侧新增"以控制器身份写 Issue 评论"的能力：delivery 已通过 GitHub Client 执行 `GET /repos/{repo}` 与 `POST /repos/{repo}/pulls`，新增 `POST /repos/{repo}/issues/{n}/comments`（控制器身份、同一凭据）即可；编码 bot 的平台工具保持禁用，写入按 ISSUE_PROTOCOL 留痕（作者、时间、轮次）。
- Review 提示词位于 `mvp/executor.ex` 的 `review_prompt`，当前已包含 "implementation and tests"，但未含本 Issue 的三个审查维度；需补入断言强度、与本 Issue 验收标准的对应关系、失败敏感性，并考虑扩展结构化输出（approved/summary）以区分实现问题与测试问题。
- 每轮成本应累计进回执与后台费用展示。

## 验收标准（草案，随边界确认后修订）

- Review 不通过且未超上限时：自动开始新一轮编码；每轮不通过理由以评论出现在原 Issue，可追溯到对应轮次。
- 超过返工上限时：任务进入 blocked，理由与轮次在 Issue 或后台可见，等待人工处理。
- 返工通过后：最终只产生一个 Draft PR，不因多轮尝试重复建 PR；人工合并仍是唯一合并途径。
- 实现附带与本 Issue 验收标准对应的测试；验收标准与测试用例的对应关系在审查结论中可追溯。
- Review 结论包含对测试本身的审查：断言强度、与验收标准的对应关系、失败敏感性；测试不合格同样构成不通过并触发打回，理由回帖 Issue。
- 全程无自动合并、无自动升级；回执与证据能完整还原每轮尝试使用的模型、费用、检查与 Review 结论。
