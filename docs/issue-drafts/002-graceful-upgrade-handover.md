建议标题：`升级接棒：A 停止领取并收尾在途任务，B 体检通过后接管，失败自动回退`

建议标签：`enhancement`（标签命名规范尚未定案，见 OPEN_QUESTIONS 第 5 项）。

## 背景：当前行为与预期的差距

自身迭代方向已确认（IS-011/012/013/014）：候选版本经真人验收合并后，需要能接替运行中的旧版本。当前缺失整个升级编排能力：

1. 官方 upstream 没有升级/交接机制：调度器持续轮询领取，没有"停止领取但继续跑完在途任务"的模式。
2. 没有"准备收工"通知通道：可选 Phoenix API 目前只有状态查询与刷新类端点。
3. 回执 at-most-once：已有回执的任务不再派发；`mix mvp.release` 仅允许归档"编码开始前失败"的回执，没有面向升级交接的批量释放语义。
4. 没有新版本启动体检与自动回退：版本切换目前只有人工流程描述，没有可执行的脚本与失败路径。

## 需求（用户已确认的流程）

升级触发前提：真人合并了版本 B 的 PR（B 通过验收，符合 IS-013 人工合并边界）。

```text
真人合并 PR（版本 B 通过验收）
        ▼
升级脚本：通知运行中的旧版本 A "准备收工"
        ▼
A 收到通知后：
  ① 立刻不再领取新任务        ← 第一步，防止边清边领
  ② 手头的会话继续跑到交出成果（交 PR、转 review 就算完）
  ③ blocked 的任务：释放领取（反正等人中），留给新版重新领
  ④ 超过等待上限：强停，任务放回 ready
  ⑤ 确认手上没活了 → 干净退出
        ▼
升级脚本：启动版本 B
  → 体检：配置能加载、能正常轮询任务单
  → 体检不过：自动重启版本 A（回退），报告失败
        ▼
B 正常运行，领取积压的新任务（按 B 的规则）
```

要点转述：

1. **先停入口，再清在途**：A 收到通知的第一步是停止领取新任务，避免"边清边领"。
2. **在途会话跑到交出成果**：以"交出 PR、转入 review"为完成口径，不要求任务全链路终结；交出后该任务的回执与证据随 A 退出保留（对齐 OPERATIONS 的"完整领取状态及 evidence 必须在升级时保留"），不是随 A 消失。
3. **blocked 任务释放领取**：等人的任务不占用 A 的收尾时间，留给 B 重新领取；范围按既有工程默认收窄——已进入编码/发布阶段或已有交付物的回执不释放（见待确认第 3 项）。
4. **有界等待**：超过等待上限强停在途会话，任务放回 ready，不无限等待；放回 ready 的任务由 B 启动时的存量 ready 扫描接住（见第 8 点）。
5. **干净退出**：确认手上没活后 A 退出，升级脚本才启动 B。
6. **体检门禁**：B 启动后先体检（escript 能在目标机启动、配置能加载、能正常轮询任务单），通过才算接管。
7. **自动回退**：体检不过自动重启版本 A，报告失败，回到升级前状态。
8. **按新规则继续**：B 正常运行后按 B 的规则领取积压任务。接管机制即 B 首次启用时对获准存量 ready Issue 的扫描（OPERATIONS 已确认该语义）；A 收尾期间放回 ready 的任务由该扫描承接。

## 待确认边界（逐项讨论后再定案）

1. **通知机制与角色划分**：升级脚本如何通知 A"准备收工"（进程信号 / 管理端点 / 控制文件）？升级脚本由谁承载（独立进程、CI、人工命令）——需满足"不由待验收候选版本自控"的既定边界。
2. **"交出成果"的判定与等待上限**：交 PR / 转 review 的判定信号来自哪里？等待上限默认多长、如何配置？强停时在途工作区的证据如何处置（保留还是丢弃）？
3. **blocked 释放的范围**：工程默认已确定（OPERATIONS / IMPLEMENTATION_V0）：完整领取状态及 evidence 在升级时保留；已进入编码/发布阶段的失败不自动重试。因此 `publish_pending`、等待人工合并及已进入编码的回执**默认不释放**，避免被 B 重新领取后重复建 PR、重复交付。仍待确认的只剩：编码开始前 blocked 回执的释放范围（`mvp.release` 目前仅允许归档这类回执），以及释放是否需人工逐条确认。
4. **任务放回 ready 的主体与标签规则**：强停后由谁恢复/确认 ready 标签？与 OPEN_QUESTIONS 第 5 项的 ready 移除/重加规则如何衔接？
5. **体检的判定标准**："能正常轮询任务单"如何探测、探测是否只读、会不会误消费正式队列？体检超时多久判失败？
6. **回退的阶段性**：B 体检不过（未接管、未写状态）时回退 A 相对安全；若 B 已接管并写入状态/交付后才故障，按 SELF_ITERATION_MVP 运行边界 7 不能盲目恢复备份，需对账。升级脚本如何区分这两个阶段并走不同回退路径？
7. **跨版本状态兼容**：回执 schema、state_dir、WORKFLOW.md 配置在 A→B 之间的兼容性；B"按 B 的规则"领取时（如 ready 标签改名、模型白名单变化），A 期间写入的回执与证据 B 能否读取？
8. **升级触发与授权**：真人合并 PR 后，升级脚本是人工执行还是自动触发？谁有权执行升级（对应 IS-013 人工合并/升级边界）？
9. **积压领取节奏**：B 接管后领取积压任务是并发上限内逐步领取还是一次性？升级窗口内用户新加的 ready 任务归属哪个版本处理？

## 实现衔接提示（工程提示，不是承诺或设计定案）

- 升级脚本是本项目新增的**外部升级入口**，官方 upstream 无此能力；它不能由候选版本 B 自身承担。
- **升级对象是运行目录工件，不是源码树**：按当前 V0 调用方式，一个版本 = 独立运行目录中的 escript（`mix build` 产出）+ 已填写的 WORKFLOW.md + state_dir + 工作区根。升级脚本替换 escript 工件与配置，不动源码树；B 启动必须带显式 guardrails 确认开关（`--i-understand-that-this-will-be-running-without-the-usual-guardrails`）。
- "通知 A"可选路径：进程信号处理、为可选 Phoenix API 增加管理端点、控制文件轮询；当前 JSON API 仅 `/api/v1/state`、`/api/v1/<issue>`、`/api/v1/refresh`。
- orchestrator 需要新增"停止领取、继续在途、上报清空"的运行模式；upstream 目前持续轮询。
- Receipt 需扩展"升级释放"语义（新增状态或归档标记），并明确哪些状态可释放、哪些（publish_pending / awaiting_human_merge）默认不可释放。
- 强停在途会话需要终止 AppServer 会话并定义工作区处置；upstream blocked 状态仅存内存，重启即清，与"B 重新发现 blocked 任务"天然衔接，但回执口径必须一致，否则 `available?` 会挡住重新派发。
- 体检可分解为：目标机可运行性（escript 能启动：Linux/WSL、Elixir 1.19.x / OTP 28、GNU timeout、原生 Linux Codex CLI，而非 `/mnt/c` 的 Windows 包装）+ 配置加载校验（类似 `mix mvp.check`，不联网派发）+ 只读轮询探测 + 启动自检日志；全部由升级脚本执行并落报告。
- 升级全程应产出留痕：通知时间、A 停止领取时间、在途任务处置清单、退出时间、体检结果、回退原因（如有）。

## 验收标准（草案，随边界确认后修订）

- 升级窗口内 A 不再领取新任务；每个在途任务的结果可追溯：要么交出成果（PR / 转 review），要么超限强停且任务回到 ready，不出现两个同时有效的执行者。
- 被释放的 blocked 任务可被 B 重新领取；已有 PR 待人工合并的任务不被重复交付、不重复建 PR。
- A 干净退出前不丢失任务：每个任务在退出时处于"已交付待审""回到 ready""由 B 接手"三种状态之一，且有记录。
- B 体检通过后才接管并按 B 的规则领取积压任务；体检失败时自动重启 A、报告失败原因，A 恢复正常领取。
- 升级与回退只作用于运行目录工件（escript、WORKFLOW.md、state_dir、工作区根），源码树与候选工作区不受影响。
- 回退后回执、证据与平台交付记录对得上：不重复扣费、不重复派发、不丢任务；仅回退二进制而未对账不算通过（对齐 SELF_ITERATION_MVP 演练表）。
- 升级全程留痕可审计：通知、收尾、退出、体检、接管或回退的每一步时间与结论可查。
