# 自动恢复与自身迭代合同

IS-031/032/033：coder 在同一次会话中自主检查并修复，达到提交条件后再由控制器执行完整验收，通过后进入独立 Review。已授权实施隔离执行并恢复 #5；四条底线、配置和验收状态见 [CODER_EXECUTION_RULES.md](CODER_EXECUTION_RULES.md)。自检不替代正式门禁。

来源：IS-026、IS-027。状态：控制器 `07f7493` 已通过完整门禁并运行；真实 Issue #3 已完成自动诊断、修复、检查失败返工、独立 Review 和 Draft PR 交付。分层证据见 [验收记录](VALIDATION_AUTOMATIC_RECOVERY.md)。本文的数值是工程默认，不是用户逐项指定的永久产品决定。

## 范围和兼容

自动恢复复用官方 Elixir 调度、工作区和 AppServer，在现有 `Mvp.Executor` 中扩展阶段控制，不另建调度器。Python 仍只承担检查和验收脚本。

`mvp.recovery.enabled` 显式为 true 才启用。未启用时保留 `mvp.max_rework=0..5`、默认 0 的旧合同，详见 [REVIEW_REWORK.md](REVIEW_REWORK.md)。策略随执行冻结到回执，不能修改运行配置就给在途任务无限增额。旧 blocked 任务不因启用策略自动接管；选定旧任务只能通过下文的审计迁移进入新策略。

## 工程默认

以下字段属于 `mvp.recovery`，配置解析及边界测试应与此表保持一致。

| 字段 | 默认 | 含义 |
| --- | --- | --- |
| `enabled` | false | 显式开启自动恢复 |
| `max_rework` | 20 | 总编码返工上限，初始编码另计；历史已用次数保留 |
| `diagnose_every` | 3 | 普通修复窗口；到达窗口进入新的只读诊断，无需逐窗人工批准 |
| `stage_attempts` | 3 | 每阶段最多三次尝试，包含首次；协议纠正和允许的阶段重试均受约束 |
| `max_agent_attempts` | 64 | 编码、Review、诊断及协议纠正的模型尝试总上限 |
| `max_elapsed_ms` | 7200000 | 自动恢复执行的总经过时间上限，两小时；不是每轮重新计时 |

同类失败已有两次历史时可提前诊断；未知检查失败立即诊断。计数、开始时间、已用用量和策略保持持久化，不因重试、诊断、失败来源切换或审计续跑而归零。旧回执迁移须记录可核实的历史次数及新策略时间锚点，不能伪造旧模型遥测；未取得的 token 和费用继续标为未知。

这些上限用于防止资源失控，不保证任意任务都能自动成功。达到上限保存终态与证据，不自动扩大预算或创建新任务规避限制。

## 阶段与恢复动作

主链为编码、完整检查、独立 Review、Draft PR 交付。故障先归类，再决定直接修复、诊断或停止。每次新编码后重新执行完整候选检查、原冻结回归及独立 Review，旧批准不覆盖新候选。

IS-035 增加外部条件停点：Review/诊断按结构化字段区分代码缺陷与外部条件；混合阻塞先修代码，外部条件仍保留。仅剩外部条件时，候选和完整证据持久进入 `awaiting_external`，不再消耗编码轮次。获准操作者通过审计入口提交绑定验收项及摘要的证据后，原候选重新完整检查和独立 Review；不能直接批准或发布。真实等待时段从活动时间扣除，原历史、策略额度和次数不归零，已经耗尽的执行额度不因接手而恢复。详细记录和命令见 [EXTERNAL_HANDOFF.md](EXTERNAL_HANDOFF.md)。

| 故障 | 处理 |
| --- | --- |
| 固定 runner 确认可修复的检查失败 | 反馈完整证据给 coder；达到诊断窗口或重复失败条件时先诊断 |
| 有效的独立 Review 拒绝 | 保存 Review 和确认评论；代码缺陷交 coder 修复，仅外部条件进入等待。原代码拒绝不得以空证据重复 Review 消除 |
| Review 或诊断协议输出非法 | 保存每次原文和准确解析错误，要求对应角色纠正；严格解析完整输出，达到阶段上限停止 |
| 未知检查错误 | 立即进入只读诊断，不能由模型直接判通过，也不把非零退出一律归为可修复断言 |
| 可恢复环境或无副作用模型阶段失败 | 诊断选择已允许的阶段重试或仓库内代码修复；仍受完整性、阶段次数和总资源限制 |
| 评论 POST 结果不确定 | 仅 GET 原 Issue 评论，唯一精确匹配已保存意图后确认并继续；零匹配、多匹配或查询失败保留现场停止 |
| 发布结果不确定 | 沿用只读交付对账，不盲目重发写操作 |
| 完整性失败、权限/范围需新增授权、无进展或资源耗尽 | 保留原始失败及尝试历史，明确 blocked 原因 |

诊断是新的只读模型会话，读取冻结的 Issue 范围、历次候选变化、检查报告及 Review，给出证据和下一步。诊断只允许返回以下动作，由程序核对适用阶段及剩余资源：

- `repair_code`：交 coder 在原仓库和原工作区内修复，随后重新执行完整门禁。
- `retry_stage`：重新执行完整检查或获准的无副作用模型阶段；不能重发平台写操作，也不能绕过有效 Review 拒绝。
- `stop`：保存诊断及明确停止原因。
- `await_external`：列明结构化外部条件、所需证据及接手责任，持久进入等待；不能覆盖已知代码缺陷。证据核验后仍重新正式检查及独立 Review。

诊断不能返回批准、修改验收、降低覆盖率、关闭检查、替换冻结 base 或模型、扩大权限，也不能安装系统组件或修改运行服务。标准检查仍由控制器执行；未启用隔离执行的兼容路径出现 Mix.PubSub socket 限制时，模型仍不能自行提权。IS-033 的隔离执行能力由控制器按新规则预先配置并验收，不由在途诊断临时扩权。

重复失败的诊断应解释与前次不同的修复假设和可验证步骤。新的提交 SHA 本身不是进展；不能靠重述反馈无限循环。重复无进展最终受总返工、模型尝试和时间熔断约束，停止时保留已经尝试的方法。

## 冻结、证据与用量

执行绑定所属仓库、Issue 范围、初始 base、候选 SHA、模型、工作区、Git 元数据、冻结基线、检查边界及恢复策略。恢复前后继续校验这些绑定；新需求不能通过诊断或模型输出成为隐式授权。

每次检查、Review、诊断和协议纠正使用独占的 attempt 证据目录，保留原始 stdout/stderr、模型输出、解析错误、退出状态、运行身份及动作决定。不得覆盖前一次 `review.json` 或检查日志来制造成功记录。检查报告缺失、截断、身份或退出码矛盾仍不能通过；诊断后若重试，必须获得新的完整有效证据。

模型用量按 attempt/session 记录，同一会话重复累计通知取最大值，不同会话相加。新尝试开始前落盘，首条消息前中断也能看到未知用量；不得沿用每轮每角色取最大值而漏掉重试成本。实际费用不可得时仍为 null，不从 token 数虚构金额。

控制器已知的技术失败恢复不等于进程崩溃后自动接管。中断留下的执行锁和不确定现场仍按审计流程核实，不能仅因进程 ID 消失就删除锁或恢复旧回执。

旧回执缺少逐会话开始标记时，全部既有 usage 槽位保守计入模型尝试上限，包括用量未知的槽位；这不把未知 token 或费用伪造成已知值。迁移建立本次获准恢复的时间窗口，原执行耗时若未完整记录则保持未知。开始恢复清空当前停止原因，旧原因仍完整保存在审计副本中。

## 验收矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| 未启用策略 | 原 0..5 行为兼容，旧回执不被自动恢复 |
| 合法修复超过五次后通过 | 无逐窗人工批准；历史计数连续，完整检查及独立 Review 通过后仅交付一个 Draft PR |
| 修复窗口或重复故障触发诊断 | 新只读会话给出有效动作，coder 据此修复，通过后续完整检查与 Review |
| Review/诊断输出协议错误 | 原始输出逐次留存，严格纠正成功后继续；无法纠正则在阶段上限停止 |
| 未知检查错误诊断后重跑 | 模型不能判通过；独占新证据目录完整重检，只有真实成功结果能进入 Review |
| 有效 Review 拒绝 | 原拒绝和评论保留；代码缺陷先修复，仅外部条件保存交接记录并等待，新外部证据核验后重检同一候选 |
| 外部条件等待与接手 | 等待不重复调用 coder/Review、不发布；审计接手核验全部绑定和证据，完整检查与新 Review 决定结果 |
| 评论写入不确定 | 仅 GET 对账；唯一匹配后继续；否则停止且不重复 POST |
| 总轮数、模型尝试或时间耗尽 | 在下一允许动作前阻止继续，计数和用量不重置，保存明确终态 |
| 候选、base、元数据、报告或回执被改动 | 阻止恢复与交付，不以诊断结果豁免完整性 |
| 旧 Review 拒绝回执迁移 | 原 Review、确认评论、摘要和操作链全部匹配才接受；并发、回滚、错误身份及未确认评论拒绝 |
