# GitHub MVP 与自身迭代验收提案

状态：平台分期、基于官方源码实现、自动 PR 与人工合并/升级已确认（IS-012/013/014）。其余机制是工程建议，验收演练尚未执行。

## 已确认目标

先实现 GitHub MVP，随后由 Symphony 迭代本项目。GitLab 后置，双平台仍是后续目标。当前已导入官方实现并增加本地扩展；没有远端仓库，尚未证明真实自身迭代能力。

## 怎样判定“能迭代自己”

建议把定义定为：运行版本 A 能领取本仓库的真实 Issue，在隔离工作区生成候选版本 B；B 经外部验证和获准切换后，能继续完成下一项自身开发任务。只产生代码或 PR，只验证了开发产出；还需证明候选版本能接替旧版本继续工作。

这是针对明确任务范围的可验收能力，不是任意需求都能自动完成的保证。遇到不明确需求、失败或超预算，可以明确阻塞交还人工。

## 建议的最小构成

| 部分 | MVP 中需要证明的能力 |
| --- | --- |
| GitHub 任务入口 | 自动发现、领取获准的 ready Issue；同一轮任务不会因重复扫描或重启同时执行两份；具体 ready 生命周期仍待定 |
| 隔离执行 | 固定运行版本 A；候选源码 B 在独立工作区修改；不能直接覆盖 A 的安装目录、状态或凭据 |
| 编码与 Review | 解析两个角色的仓库默认及评论覆盖；调用编码 Agent 和独立 Review；模型可用性与使用权限需另行核实 |
| 可重复验证 | 项目有明确的准备、启动、测试命令；验收可以由任务外执行，检查固定候选 SHA |
| 结果与恢复 | 建议交付 PR、检查结果、日志、尝试编号及用量；错误可定位，超时/返工有界，阻塞可人工恢复 |
| 版本切换 | 建议由外部升级入口安装已验收的固定版本；状态兼容或备份恢复；保留旧版可用回退入口 |

“外部”表示不由待验收候选版本独自控制，可由独立进程或 CI 承担，不要求新增一套大型服务。后台仍保留已确认的查看与默认配置入口；真实后台各项能力的 MVP 深度尚待确认。

## 建议的运行边界

1. 人与开发 Agent 先完成可运行的 V0；V0 建立前，不能要求未实现的 Symphony 完成第一次自举。
2. V0 使用已安装的固定版本，开发工作只发生在候选源码工作区。
3. 候选版本可以新增测试，但验收包含事先确定、由任务外维护的基线。修改验收规则、授权、状态迁移或升级机制时需额外审查，不能靠删测试或降低标准获得通过。
4. Review、构建产物与测试结果绑定同一个候选 SHA；新增提交后旧结论不覆盖新代码。
5. 候选版本使用独立测试状态和测试任务范围验证，不能与当前版本同时消费正式队列。
6. 建议 MVP 自动执行到可审核 PR；人工确认合并及升级。升级入口先停止接入并处理在途任务，再备份与切换；失败时恢复兼容状态及旧版本。该人工边界已由 IS-013 确认。
7. 若新版本已经接管任务并写入状态后才故障，不能直接覆盖为升级前备份。回退流程需保留并核对接管后的领取、提交、PR 与完成记录，通过兼容读取、迁移或可验证的重放恢复；无法确定某次平台写入结果时，先阻塞并对账，不能盲目重发。具体存储方案未定。

## 建议的验收演练

| 演练 | 通过证据 |
| --- | --- |
| 第一次自身修改 | V0 领取本项目一个预先定义验收条件的小功能或缺陷 Issue，自动产出实现、回归测试与可审核 PR；人工不替它补实现代码，介入如实记录 |
| 候选版本接棒 | 验收并获准切换到 V1 后，由 V1 领取另一项自身功能/缺陷任务，产出 V2 候选；第二轮不能仍由 V0 执行 |
| 失败门禁 | 引入受控的失败候选，证明检查失败会阻止升级，旧版本仍可执行；独立 Review 也不能替代机器检查 |
| 重启与重复发现 | 执行中中断后重启、重复扫描同一任务，证明不会出现两个同时有效的执行者或重复有效交付；具体恢复与重试合同需先确认 |
| 升级失败与回退 | 在测试环境分别演练切换时失败，以及 V1 已接管任务并写入状态/交付后才故障；恢复旧版本和兼容状态，与平台交付记录对账后再接任务，确认不丢失任务或重复有效交付。只回退二进制或盲目恢复旧备份不算成功 |

以上是建议的 MVP 完成门槛，尚未执行。保存 Issue、运行版本、候选 SHA、Review、检查记录、升级/回退结果，才能判断链路在哪一段成立或失效。一次文案修改或截图演示不足以替代上述演练。
