# GitHub MVP 与自身迭代验收边界

状态：平台分期、基于官方源码实现、自动 PR 与人工合并/升级已确认（IS-012/013/014）；自动技术恢复方向按 IS-026 实施。真实 GitHub 已接入，历史交付不等于本轮自动恢复已验收。完整 A/B 自动升级接棒与回退仍是后续提案。

先实现 GitHub MVP，随后由 Symphony 迭代本项目。GitLab 后置，双平台仍是后续目标。已基于官方 Elixir 实现增加本地扩展，并建立私有仓库 `dailiuyi/innovation-symphony`。Issue #1 曾经操作者明确协助续跑后交付 PR #2，用户已合并并授权切换运行版本（IS-018/019）。这些证明历史接入和交付，不证明全过程无需人工技术干预。

本轮按 IS-026 完善有界自动恢复，并通过明确选定的 Issue #3 验证真实链路。当前任务范围仍是只读 `--preflight`；不得把完整升级接棒、自动回退或云部署加入该 Issue 的验收要求。源码、标准门禁、运行版本、真实恢复和 Draft PR 交付须分别记录。

## 怎样判定“能迭代自己”

本轮验证的闭环是：固定运行版本领取或经审计接续获准的本仓库任务，在隔离工作区编码，自动处理可恢复技术失败，通过完整检查和独立 Review，交付同一候选 SHA 的 Draft PR。超过五次修复、诊断反馈到编码、协议纠正及失败熔断都必须有真实状态和证据，不能靠人工直接修候选补齐。

后续还可演练：候选版本经人工合并及获准切换后继续完成下一项自身任务，以证明版本接棒。完整自动升级及故障回退的机制和演练仍待单独确认，不是本次自动修复的强制交付。

这是针对明确范围的可验收能力，不是任意需求都能自动完成的保证。模型能处理的技术问题不逐次交还人工；缺少需求决策或权限、完整性失败、远端结果无法对账、无进展及资源耗尽仍应明确停止。

## 建议的最小构成

| 部分 | MVP 中需要证明的能力 |
| --- | --- |
| GitHub 任务入口 | 自动发现、领取获准的 ready Issue；同一轮任务不会因重复扫描或重启同时执行两份；具体 ready 生命周期仍待定 |
| 隔离执行 | 固定运行版本 A；候选源码 B 在独立工作区修改；不能直接覆盖 A 的安装目录、状态或凭据 |
| 编码与 Review | 解析两个角色的仓库默认及评论覆盖；调用编码 Agent 和独立 Review；模型可用性与使用权限需另行核实 |
| 可重复验证 | 项目有明确的准备、启动、测试命令；验收可以由任务外执行，检查固定候选 SHA |
| 结果与恢复 | 自动交付 Draft PR、检查结果、完整日志、尝试编号及用量；按 IS-026 自动诊断和恢复，受完整性及总资源门禁约束 |
| 版本切换 | 人工确认安装固定版本；完整 A/B 自动接棒、状态迁移和回退机制为后续提案，不是本次交付条件 |

“外部”表示不由待验收候选版本独自控制，可由独立进程或 CI 承担，不要求新增一套大型服务。后台仍保留已确认的查看与默认配置入口；真实后台各项能力的 MVP 深度尚待确认。

## 建议的运行边界

1. 人与开发 Agent 先完成可运行的 V0；V0 建立前，不能要求未实现的 Symphony 完成第一次自举。
2. V0 使用已安装的固定版本，开发工作只发生在候选源码工作区。
3. 候选版本可以新增测试，但验收包含事先确定、由任务外维护的基线。修改验收规则、授权、状态迁移或升级机制时需额外审查，不能靠删测试或降低标准获得通过。
4. Review、构建产物与测试结果绑定同一个候选 SHA；新增提交后旧结论不覆盖新代码。
5. 候选版本使用独立测试状态和测试任务范围验证，不能与当前版本同时消费正式队列。
6. MVP 自动执行到可审核 Draft PR；人工确认合并及升级，这一边界已由 IS-013 确认。停止接入、处理在途任务、备份、切换及失败恢复属于后续完整升级方案，具体自动化机制不能当作已批准默认。
7. 若新版本已经接管任务并写入状态后才故障，不能直接覆盖为升级前备份。回退流程需保留并核对接管后的领取、提交、PR 与完成记录，通过兼容读取、迁移或可验证的重放恢复；无法确定某次平台写入结果时，先阻塞并对账，不能盲目重发。具体存储方案未定。

## 本轮必须验证

按 [自动恢复验收矩阵](AUTOMATIC_RECOVERY.md) 验证超过五次自动修复、诊断到修复闭环、协议错误纠正、未知检查诊断重跑、资源熔断、完整性与旧 Review 回执迁移。模拟模型和平台只能验证程序合同；真实 #3 必须另有固定运行版本、原 base、冻结模型、候选 SHA、逐次证据、最终 Review 和实际 Draft PR。

目前这些新增项目待验证。#3 的合法 Review 拒绝必须交回 coder 修复，再完整检查和独立 Review；操作者不直接修改候选。旧任务迁移须保存授权、原回执摘要和操作链，不能重新领取或重置预算。

## 历史交付与后续演练提案

| 演练 | 通过证据 |
| --- | --- |
| 第一次自身修改 | 历史 Issue #1/PR #2 已交付并获准切换；操作者介入按 IS-017/018 如实保留，不能据此宣称无干预闭环 |
| 候选版本接棒 | 后续可在人工验收并获准切换到 V1 后，由 V1 领取另一项自身任务并产出 V2；该演练与本次 #3 自动修复分别报告 |
| 失败门禁 | 引入受控的失败候选，证明检查失败会阻止升级，旧版本仍可执行；独立 Review 也不能替代机器检查 |
| 重启与重复发现 | 执行中中断后重启、重复扫描同一任务，证明不会出现两个同时有效的执行者或重复有效交付；具体恢复与重试合同需先确认 |
| 升级失败与回退 | 在测试环境分别演练切换时失败，以及 V1 已接管任务并写入状态/交付后才故障；恢复旧版本和兼容状态，与平台交付记录对账后再接任务，确认不丢失任务或重复有效交付。只回退二进制或盲目恢复旧备份不算成功 |

表中接棒、重启恢复和升级回退为后续演练提案，不是本次新增强制门槛。历史完成项以决策记录及运行证据为准，其余不能宣称已执行。保存 Issue、运行版本、候选 SHA、Review、检查记录及实际切换结果，才能判断链路成立到哪一步。
